# Building and publishing

**English** · [Português](building.pt-BR.md)

How to build Mr Keyboard on your computer or with GitHub Actions, and how a release is published. Back to the [README](../README.md).

## What is in the repository
This repository holds the app as an [apktool](https://apktool.org/) project (smali code and resources). It also has:
- `native/`: the C++ dictionary reader, `libjni_pckeyboard.so` (CMake);
- `engine/`: the native suggestion engine, `libmrengine.so` (correction search and two-word prediction in C++, with the Java code as fallback; see [`docs/native-engine.md`](native-engine.md));
- `docs/`: notes for each version (in Portuguese) and the tools used to build the dictionary and the Java classes.

## From a release (download, edit, build)
every [release](https://github.com/x-mrrobot-x/mr-keyboard/releases) has `mr-keyboard-v<version>-source.zip`, made from the exact commit that was published. It holds the apktool project (`smali/`, `res/`, `lib/`, `apktool.yml`), `native/` and `engine/`, the Java-layer sources (`docs/tools/java`, with `build_java.sh`), the licence, the READMEs and this guide. The dictionaries are not in it: they are in the dictionary zips of the releases and in `dicts/` in the repository. To change the app, unzip it, edit `smali/` and `res/`, and build and sign as shown in *Locally* below. Two things to know about a build signed with your own key: Android only installs it over the original app after that one is uninstalled (its settings are lost), and the app only accepts a dictionary catalog signed with its own key, so a fork needs its own releases (the *Mr Keyboard - APK* workflow makes them) and the repository address in `docs/tools/java/src/com/mrkeyboard/app/MrPacks.java` changed to yours.

## With GitHub Actions
There are three workflows:
- *Mr Keyboard - APK* runs on every push that changes the app (`smali/`, `res/`, `lib/`, `apktool.yml`). It builds the APK with apktool 2.11.1 using the libraries already in `lib/`, and signs it if these secrets exist: `KEYSTORE_B64`, `KEYSTORE_PASS`, `KEY_ALIAS`, `KEY_PASS`. Without the secrets (in a fork, for example), you get an unsigned APK in the `apk` artifact. To publish, it first runs *Mr Keyboard - checks* and only goes on if they all pass; the job that creates the release is the only one with write permission.
- *Mr Keyboard - native lib* runs only when `native/` or `engine/` changes (or by hand). It builds both libraries for arm64-v8a, armeabi-v7a, x86 and x86_64 with NDK 27 and runs the PC tests. Extract its `native-libs` artifact at the project root (merging with `lib/`) and commit `lib/`, `native-src.sha256`, `mrengine-src.sha256` and `mrengine-info.txt`. The APK workflow compares those hashes with the current `native/` and `engine/` and refuses to publish if `lib/` is out of date.
- *Mr Keyboard - checks* runs on pushes to `main` and on pull requests that change the app. It checks the version and release notes, the resources (including the Spanish strings), the "Restore defaults" key list, the smali registers and that the generated Java-layer smali is up to date, builds the app to verify the dex, runs the PC tests and checks that the native engine gives exactly the same results as the Java code (Java x C++, three languages). The same scripts are in `docs/tools/` and run on your computer too. `check_workflows.py` also checks the workflows themselves: every action pinned by commit, minimal permissions, and publishing only after the checks.

## Publishing (maintainers)
- **Immutable releases (once, by the repository owner):** in *Settings → Releases*, turn on *Enable release immutability* **before** the first release made by this workflow. It only applies to releases published after it is on. From then on the files and the tag of a published release can never be changed or deleted, and the name of its tag can never be used again, so a wrong release is fixed with a new version, never by editing the old one. Releases made before it was turned on stay mutable. The workflow already does what GitHub recommends: it creates the release as a draft, attaches everything and only then publishes it.
- **One release per launch:** raise `versionCode` and `versionName` in `apktool.yml`, write the notes in `docs/release-notes/<tag>.md` (e.g. `docs/release-notes/v1.72.0.md`, with a **Português** block and an **English** block, as a changelog: one item per change, starting with **New**, **Improved** or **Fixed** (**Novo**, **Melhorado**, **Corrigido** in Portuguese), told from the user's side) and push to `main`. *Mr Keyboard - APK* publishes a single [release](https://github.com/x-mrrobot-x/mr-keyboard/releases), tagged with `versionName` (e.g. `v1.72.0`), with the signed APK (`mr-keyboard-v1.72.0.apk`, the version is in the file name), the source code of that commit (`mr-keyboard-v1.72.0-source.zip`), a signed `catalog.json`, a signed `update.json` (the version, the size and SHA-256 of the APK and the notes in Portuguese and English, taken from the two blocks of the notes file, and in Spanish when the file has an **Español** block) and only the zips of the dictionary languages that changed in this version. Both JSON files are signed with the same key as the APK, each with its own prefix, so one can never be taken for the other. The APK and the source zip get a build provenance attestation. The text is the notes file (without the **Español** block), the list of included dictionaries (with the ones that are new in this version) and the checksums. It needs the signing secrets; without them, with a version that is already published, or with an out-of-date `lib/`, it only warns and the APK stays in the `apk` artifact. Running it by hand with *publish* checked does the same, but treats any of these as an error. The release is created as a draft, its files are checked, and only then it is published.
- **Notes of the next release:** they can be written ahead, in the file of the version that comes next (`docs/release-notes/v2.1.0.md` for 2.1.0), while `apktool.yml` still has the published version: what makes a push publish a release is a new `versionName` in `apktool.yml`, not a notes file.
- **Spanish notes (only inside the app):** the same notes file may end with an **Español** block (same items, labels **Nuevo**, **Mejorado**, **Corregido**, **Cómo obtenerla**). The GitHub Release stays in Portuguese and English: `publish_release.sh` leaves that block out of the Release text (`python3 docs/tools/make_update.py --release-text docs/release-notes/<tag>.md` prints it). The block reaches the phone in two places: the notes of the installed version (Settings → About → Version), which are `assets/mr_release_notes.md` inside the APK (the APK build copies `docs/release-notes/<tag>.md` there by itself before apktool runs, so there is nothing to do by hand; the copy committed in `assets/` is the one local builds and the tests read, and `docs/tools/check_version.py` only warns when it is out of date), and the update notice (`notes.es` of `update.json`). An app in a language with no block shows English; an old app ignores `notes.es`.
- **Dictionaries:** the packs live in `dicts/<language>/` (`pack.json` lists the files). Each zip is named `mr-keyboard-dict-<id>-<version>.zip` and is attached **only to the release where that language changed**; the catalog says, for each language, which release holds its zip (`release`), and the app builds the download address from it. After a change, raise `version` in that `pack.json` **and** the app version, and push: the new release brings the new zip and a `catalog.json` with a higher `serial`. Languages that did not change keep pointing to the release that made their zip, and nothing is copied. **Never delete or change a release that still holds a dictionary the catalog uses:** the script checks this before publishing and stops with an error naming the missing zip. The catalog is signed with the app's own key (the same one that signs the APK), and the app only accepts catalogs signed with the key it was installed with.

## Locally
```sh
apktool b . -o mr-keyboard-unsigned.apk
zipalign -p -f 4 mr-keyboard-unsigned.apk aligned.apk
apksigner sign --ks your-key.jks --out mr-keyboard.apk aligned.apk
```
