# Compilar e publicar

[English](building.md) · **Português**

Como compilar o Mr Keyboard no seu computador ou pelo GitHub Actions, e como uma release é publicada. Voltar ao [README](../README.pt-BR.md).

## O que há no repositório
Este repositório guarda o app como projeto do [apktool](https://apktool.org/) (código smali e recursos). Também tem:
- `native/`: o leitor de dicionário em C++, `libjni_pckeyboard.so` (CMake);
- `engine/`: o motor nativo de sugestões, `libmrengine.so` (busca de correção e previsão por duas palavras em C++, com o código Java de reserva; veja [`docs/native-engine.md`](native-engine.md));
- `docs/`: anotações de cada versão e as ferramentas usadas para gerar o dicionário e as classes Java.

## A partir de uma release (baixar, editar, compilar)
toda [release](https://github.com/x-mrrobot-x/mr-keyboard/releases) tem o `mr-keyboard-v<versão>-source.zip`, feito do commit exato que foi publicado. Ele traz o projeto do apktool (`smali/`, `res/`, `lib/`, `apktool.yml`), `native/` e `engine/`, as fontes da camada Java (`docs/tools/java`, com o `build_java.sh`), a licença, os READMEs e este guia. Os dicionários não vão nele: ficam nos zips de dicionário das releases e em `dicts/` no repositório. Para mudar o app, descompacte, edite `smali/` e `res/` e compile e assine como em *No computador*, mais abaixo. Duas coisas sobre uma compilação assinada com a sua chave: o Android só instala por cima do app original depois de desinstalar o original (as configurações dele se perdem), e o app só aceita catálogo de dicionários assinado com a própria chave, então um fork precisa das suas próprias releases (o workflow *Mr Keyboard - APK* faz isso) e do endereço do repositório em `docs/tools/java/src/com/mrkeyboard/app/MrPacks.java` trocado pelo seu.

## Pelo GitHub Actions
São três workflows:
- *Mr Keyboard - APK* roda a cada push que muda o app (`smali/`, `res/`, `lib/`, `apktool.yml`). Gera o APK com o apktool 2.11.1 usando as bibliotecas que já estão em `lib/` e assina, se existirem os secrets `KEYSTORE_B64`, `KEYSTORE_PASS`, `KEY_ALIAS` e `KEY_PASS`. Sem os secrets (num fork, por exemplo), sai um APK sem assinatura no artefato `apk`. Para publicar, ele roda antes o *Mr Keyboard - checks* e só segue se tudo passar; o job que cria a release é o único com permissão de escrita.
- *Mr Keyboard - native lib* roda só quando `native/` ou `engine/` muda (ou à mão). Compila as duas bibliotecas para arm64-v8a, armeabi-v7a, x86 e x86_64 com o NDK 27 e roda os testes no PC. Extraia o artefato `native-libs` na raiz do projeto (mesclando com `lib/`) e faça o commit de `lib/`, `native-src.sha256`, `mrengine-src.sha256` e `mrengine-info.txt`. O workflow do APK compara esses hashes com o `native/` e o `engine/` atuais e não deixa publicar se a `lib/` estiver desatualizada.
- *Mr Keyboard - checks* roda nos pushes na `main` e nos pull requests que mudam o app. Confere a versão e as notas, os recursos (inclusive os textos em espanhol), a lista de chaves do "Restaurar padrões", os registradores do smali e se o smali gerado da camada Java está em dia, monta o app para verificar o dex, roda os testes de PC e confere que o motor nativo dá exatamente o mesmo resultado que o código Java (Java x C++, três idiomas). Os mesmos scripts estão em `docs/tools/` e rodam também no seu computador. O `check_workflows.py` confere também os próprios workflows: toda action fixada por commit, permissões mínimas e publicação só depois dos checks.

## Publicar (para quem mantém o projeto)
- **Releases imutáveis (uma vez, pelo dono do repositório):** em *Settings → Releases*, ligue *Enable release immutability* **antes** da primeira release feita por este workflow. Vale só para releases publicadas depois de ligar. Daí em diante os arquivos e a tag de uma release publicada nunca mais mudam nem são apagados, e o nome da tag nunca mais pode ser usado, então uma release errada se corrige com uma versão nova, nunca editando a antiga. As releases feitas antes de ligar continuam editáveis. O workflow já faz o que o GitHub recomenda: cria a release como rascunho, anexa tudo e só então publica.
- **Uma release por lançamento:** aumente `versionCode` e `versionName` no `apktool.yml`, escreva as notas em `docs/release-notes/<tag>.md` (ex.: `docs/release-notes/v1.72.0.md`, com um bloco **Português** e um **English**, no estilo changelog: um item por mudança, começando com **Novo**, **Melhorado** ou **Corrigido** (**New**, **Improved**, **Fixed** em inglês), contado do lado de quem usa) e faça o push na `main`. O *Mr Keyboard - APK* publica uma única [release](https://github.com/x-mrrobot-x/mr-keyboard/releases), com a tag do `versionName` (ex.: `v1.72.0`), com o APK assinado (`mr-keyboard-v1.72.0.apk`, a versão está no nome do arquivo), o código-fonte daquele commit (`mr-keyboard-v1.72.0-source.zip`), um `catalog.json` assinado, um `update.json` assinado (a versão, o tamanho e o SHA-256 do APK e as notas em português e inglês, tiradas dos dois blocos do arquivo de notas, e em espanhol quando o arquivo tem um bloco **Español**) e só os zips dos idiomas de dicionário que mudaram nesta versão. Os dois JSON são assinados com a mesma chave do APK, cada um com o seu prefixo, então um nunca vale pelo outro. O APK e o zip do código ganham uma atestação de procedência do build. O texto é o arquivo de notas (sem o bloco **Español**), a lista dos dicionários incluídos (com os que são novos nesta versão) e os hashes. Precisa dos secrets de assinatura; sem eles, com uma versão que já foi publicada ou com a `lib/` desatualizada, só avisa e o APK fica no artefato `apk`. Rodar à mão com *publish* marcado faz o mesmo, mas trata qualquer um desses casos como erro. A release é criada como rascunho, os arquivos são conferidos e só então ela é publicada.
- **Notas da próxima release:** podem ser escritas antes, no arquivo da versão que vem a seguir (`docs/release-notes/v2.1.0.md` para a 2.1.0), enquanto o `apktool.yml` ainda tem a versão publicada: o que faz um push publicar uma release é um `versionName` novo no `apktool.yml`, não um arquivo de notas.
- **Notas em espanhol (só dentro do app):** o mesmo arquivo de notas pode terminar com um bloco **Español** (mesmos itens, prefixos **Nuevo**, **Mejorado**, **Corregido**, **Cómo obtenerla**). A release no GitHub continua em português e inglês: o `publish_release.sh` deixa esse bloco fora do texto da release (`python3 docs/tools/make_update.py --release-text docs/release-notes/<tag>.md` mostra o resultado). O bloco chega ao celular em dois lugares: as notas da versão instalada (Ajustes → Sobre → Versão), que são o `assets/mr_release_notes.md` dentro do APK (o build do APK copia o `docs/release-notes/<tag>.md` para lá sozinho, antes do apktool, então não há nada a fazer à mão; a cópia commitada em `assets/` é a que os builds locais e os testes leem, e o `docs/tools/check_version.py` só avisa quando ela está desatualizada), e o aviso de atualização (`notes.es` do `update.json`). O app num idioma sem bloco mostra inglês; um app antigo ignora o `notes.es`.
- **Dicionários:** os pacotes ficam em `dicts/<idioma>/` (o `pack.json` lista os arquivos). Cada zip se chama `mr-keyboard-dict-<id>-<version>.zip` e é anexado **só à release em que aquele idioma mudou**; o catálogo diz, para cada idioma, qual release guarda o zip (`release`), e o app monta o endereço de download a partir dela. Depois de mudar algo, aumente `version` nesse `pack.json` **e** a versão do app e faça o push: a release nova traz o zip novo e um `catalog.json` com `serial` maior. Os idiomas que não mudaram continuam apontando para a release que fez o zip deles, sem copiar nada. **Nunca apague nem altere uma release que ainda guarda um dicionário usado pelo catálogo:** o script confere isso antes de publicar e para com um erro que diz qual zip falta. O catálogo é assinado com a própria chave do app (a mesma que assina o APK), e o app só aceita catálogo assinado com a chave com que foi instalado.

## No computador
```sh
apktool b . -o mr-keyboard-unsigned.apk
zipalign -p -f 4 mr-keyboard-unsigned.apk aligned.apk
apksigner sign --ks sua-chave.jks --out mr-keyboard.apk aligned.apk
```
